      01 /
How I work

      
Four habits from debugging production that I bring to engineering.

    

    

      

        
Evidence first

        
I debug from evidence, not guesses.

        
Logs, request IDs, HAR files, a clean repro. I find where a failure actually happens before I touch anything, and that's how I approach my own code too.

      

      

        
Both sides of the ticket

        
I know what makes a bug easy to fix.

        
I've spent months writing escalations for R&D and seeing which ones get fixed fast. So I write code that's easy to debug: clear errors, useful logs, no mystery failures.

      

      

        
Fast learner

        
New tool on Monday, daily driver by Friday.

        
Coralogix, OpenSearch, HAR analysis and the Gong platform were all new to me in May 2026. Within months I was ranked #1 on the project.

      

      

        
Build it properly

        
Plan it, build it, test it.

        
FlyFourward taught me the hard way: skip the design and the code falls apart. Now I start from requirements, keep code modular, test where modules meet, and track work on a Kanban board.

Pneumonia detection from chest X-rays

              academic · solo
            

            
I trained and compared four image classifiers on 5,800+ chest X-rays: a CNN I built from scratch, plus ResNet50, MobileNetV2 and DenseNet121 using transfer learning. Then I asked the important question: where is the model actually looking?

            
    
              
  • Data augmentation, a 70/30 validation split and EarlyStopping to fight overfitting
    • 
              
  • Evaluated with confusion matrices, precision/recall and ROC/AUC, not just accuracy
    • 
              
  • Used Grad-CAM heatmaps to check each model was focusing on the lungs. DenseNet121 gave the most localised, readable focus
    • 
              
  • Added an SVM as a classical machine-learning comparison
    •

Deadlock lab
academic · solo

        
An agent-based simulation of processes competing for shared resources in a distributed system. I tested two-phase locking (2PL) and cycle-based deadlock detection across 64 configurations, then analysed how they affected throughput and contention.

        
    
          
  • Finding: with both mechanisms off and fewer resources than processes, no tasks completed at all
    • 
          
  • Turning 2PL and deadlock detection on together gave the most completed tasks
    •
